Verify CloudWatch Monitoring for ECS and ALB
Sathvik, let's verify that your deployed application is being monitored correctly in AWS CloudWatch.
We'll check your existing DevOps architecture: ALB → ECS Fargate → CloudWatch Logs, Metrics, Alarms, and Dashboard.
1. Understand what you need to verify
Application Load Balancer
Request count · Latency · HTTP 5XX errors · Healthy targets

ECS Fargate
CPU · Memory · Running tasks · Deployment status

Amazon CloudWatch
Metrics · Logs · Alarms · Dashboard · Notifications


Your verification should confirm that metrics are arriving, application logs are being written, alarms evaluate correctly, and alerts can reach the intended recipients.
2. Verify ECS CPU and memory metrics
Open AWS CloudWatch:
1. Go to CloudWatch → Metrics → All metrics.
2. Select ECS → ECS/ContainerInsights if Container Insights is enabled.
3. Select the cluster devops-training-cluster.
4. Check CPU and memory utilization for your service.
You can also query the standard ECS metrics using AWS CLI:
aws cloudwatch list-metrics \
  --namespace AWS/ECS \
  --metric-name CPUUtilization \
  --dimensions Name=ClusterName,Value=devops-training-cluster \
  --region ap-south-1


For memory:
aws cloudwatch list-metrics \
  --namespace AWS/ECS \
  --metric-name MemoryUtilization \
  --dimensions Name=ClusterName,Value=devops-training-cluster \
  --region ap-south-1


These metrics are available when the corresponding ECS service metrics have been emitted. Container-level and additional task metrics may require Container Insights.
3. Verify ALB metrics
Check the ALB metrics under CloudWatch → Metrics → ApplicationELB.
Metric	What it tells you
RequestCount	Number of requests handled
TargetResponseTime	Time taken for targets to respond
HTTPCode_ELB_5XX_Count	Server errors generated by the load balancer
HTTPCode_Target_5XX_Count	Server errors returned by targets
HealthyHostCount	Number of healthy targets
UnHealthyHostCount	Number of unhealthy targets
Use the following command to discover ALB request-count metrics:
aws cloudwatch list-metrics \
  --namespace AWS/ApplicationELB \
  --metric-name RequestCount \
  --region ap-south-1


Select your actual load balancer and target group dimensions in CloudWatch when creating graphs or alarms. ALB metrics are generally published at one-minute intervals when traffic is flowing; a lack of requests can affect which metrics appear.
4. Verify application logs
Your ECS task definition uses this expected log group:
/ecs/devops-training-app
Check that it exists:
aws logs describe-log-groups \
  --log-group-name-prefix /ecs/devops-training-app \
  --region ap-south-1


List the streams:
aws logs describe-log-streams \
  --log-group-name /ecs/devops-training-app \
  --order-by LastEventTime \
  --descending \
  --limit 5 \
  --region ap-south-1


If streams exist, inspect recent events:
aws logs tail /ecs/devops-training-app \
  --since 1h \
  --region ap-south-1


If there are no logs, check the ECS task execution role, log group name, AWS region, and container startup errors. Your application must also write useful logs to stdout or stderr.
5. Verify CloudWatch alarms
List your alarms:
aws cloudwatch describe-alarms \
  --region ap-south-1 \
  --query 'MetricAlarms[*].[AlarmName,StateValue,StateReason]' \
  --output table


For your training environment, verify alarms for:
- ECS CPU utilization.
- ECS memory utilization.
- ALB HTTP 5XX errors.
- Unhealthy ALB targets.
- Application error rate, if you've configured a custom metric or metric filter.
Alarm states mean:
- OK — the configured condition is not currently breached.
- ALARM — the threshold has been breached.
- INSUFFICIENT_DATA — CloudWatch lacks enough data to evaluate the alarm.
An OK state alone does not prove monitoring works. Verify the alarm's metric, dimensions, threshold, evaluation periods, and notification actions.
6. Verify your CloudWatch dashboard and notifications
In the AWS Console:
1. Open CloudWatch → Dashboards.
2. Open your DevOps dashboard.
3. Check ECS CPU/memory, ALB request count, latency, 5XX errors, and target health.
4. Open CloudWatch → Alarms and inspect each alarm.
5. Verify notification actions and the relevant Amazon SNS topic.
6. Check the SNS subscription status and confirm that a test notification reaches the intended recipient.
If you haven't created the dashboard or alarms yet, these steps are a verification checklist—not proof that those resources already exist.
