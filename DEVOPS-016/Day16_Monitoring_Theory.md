1. Objective

The objective of this task is to understand the fundamentals of Monitoring, Logging, Alerts, Metrics, and Observability before working with AWS CloudWatch.

A DevOps engineer must be able to understand the health and behavior of applications and infrastructure.

The basic concept is:

Application / Server
        │
        ├── Metrics
        │
        ├── Logs
        │
        └── Events
              │
              ↓
         Monitoring
              │
              ↓
           Analysis
              │
              ↓
            Alert
              │
              ↓
       DevOps Engineer

Monitoring helps answer:

"Is the system working correctly?"

Observability helps answer:

"Why is the system behaving this way?"

2. What is Monitoring?
Definition

Monitoring is the process of continuously collecting and observing information about systems, applications, servers, networks, and infrastructure to determine whether they are operating normally.

Monitoring allows DevOps engineers to identify:

High CPU usage
High memory usage
Disk usage
Network problems
Application failures
Server downtime
Increased response time
Error rates
Infrastructure availability

Example:

EC2 Server
    │
    ├── CPU: 35%
    ├── Network: Normal
    ├── Status: Healthy
    └── Disk: 60%

A monitoring system collects this information and makes it available to engineers.

3. Why is Monitoring Important?

Without monitoring, a DevOps engineer may not know that a production system is experiencing a problem until users report it.

Without monitoring
Production Server
      ↓
Problem occurs
      ↓
Users experience errors
      ↓
Customer reports issue
      ↓
DevOps Engineer investigates
With monitoring
Production Server
      ↓
Metrics collected
      ↓
Threshold exceeded
      ↓
Alert generated
      ↓
DevOps Engineer investigates
      ↓
Problem resolved

Monitoring therefore helps organizations detect problems earlier.

4. What is Logging?
Definition

Logging is the process of recording events, messages, errors, and activities generated by applications, operating systems, containers, and infrastructure.

Logs provide detailed information about what happened inside a system.

Example:

2026-09-13 10:30:12 INFO Application started
2026-09-13 10:31:20 INFO User request received
2026-09-13 10:31:25 ERROR Database connection failed

These records are called log events.

5. Why are Logs Important?

Logs help engineers investigate problems.

Suppose monitoring reports:

CPU = 95%

The metric tells us what is happening, but it may not explain why.

The application logs may show:

ERROR: Database connection timeout
ERROR: Retry attempt 5

Now the engineer has additional information for troubleshooting.

Therefore:

Metrics
   ↓
Detect problem

Logs
   ↓
Investigate problem
6. What is an Alert?
Definition

An alert is a notification generated when a monitored condition meets a defined rule or threshold.

Example:

CPU Usage
    │
    ↓
85%
    │
    ↓
Threshold = 80%
    │
    ↓
ALERT
    │
    ↓
DevOps Engineer

An alert can notify engineers through approved notification or incident-management systems.

7. Example of an Alert

Suppose a production server has a CPU threshold of 80%.

Configuration:

Metric:
CPU Utilization

Condition:
CPU > 80%

Duration:
5 minutes

If CPU remains above 80% for the configured evaluation period:

CPU
 │
90% ──────────────
 │              │
80% ────────────┼── Threshold
 │              │
70%             │
 │              │
 └──────────────┴──────── Time
                 ↓
               ALERT

The alert can inform the DevOps team that the server requires investigation.

8. What is Observability?
Definition

Observability is the ability to understand the internal state and behavior of a system by examining the information it produces.

Observability goes beyond simply asking whether a system is healthy.

It helps engineers investigate questions such as:

Why did the application become slow?
Why are requests failing?
Which service is causing the problem?
Where did the request fail?
Why did CPU usage increase?
Why did latency increase?
Which dependency is unavailable?

A useful conceptual model is:

                 Observability
                      │
       ┌──────────────┼──────────────┐
       ↓              ↓              ↓
    Metrics          Logs          Traces
       │              │              │
       ↓              ↓              ↓
    Numbers         Events       Request Flow

The three commonly discussed observability signals are:

Metrics
Logs
Traces
9. Monitoring vs Observability

Monitoring and observability are related but are not identical.

Monitoring	Observability
Shows system health	Helps understand system behavior
Often focuses on known conditions	Helps investigate unknown problems
Uses metrics, logs, alerts	Uses metrics, logs, traces and context
Detects problems	Helps investigate causes
Answers "Is something wrong?"	Helps answer "Why is it wrong?"

Simple example:

Monitoring:
"CPU is 95%."

Observability:
"CPU is 95% because a particular application process
is repeatedly performing expensive operations."

DevOps engineers monitor servers to maintain:

Reliability

Monitoring also helps with:

11. What Happens if a Production Server Reaches 100% CPU?

When a production server reaches 100% CPU utilization, the CPU is fully occupied.

The exact impact depends on the workload and architecture, but possible consequences include:

Application requests become slower
Response times increase
Background processes may be delayed
Requests may time out
Health checks may fail
Application errors may increase
Users may experience slow or unavailable services
Other processes may not receive sufficient CPU time

Architecture:

Production Server
       │
       ↓
CPU = 100%
       │
       ├── Application slows
       ├── Requests increase in latency
       ├── Timeouts may occur
       └── Users experience problems

A high CPU value does not automatically mean the server has failed. Engineers must investigate the cause.

Possible causes include:

Unexpected traffic
Inefficient application code
CPU-intensive background jobs
Infinite loops
Resource-intensive queries
Misconfigured processes
Malware or unexpected workloads
Insufficient server capacity

13. Why Should Monitoring Be Configured Before a Production Incident?

Monitoring should be configured before an incident because monitoring is most useful when it is already collecting historical information and has working alerting rules.

If monitoring is configured only after a production problem begins:

Incident
   ↓
Engineer notices problem
   ↓
Monitoring is not configured
   ↓
No historical metrics
   ↓
No predefined alerts
   ↓
Investigation becomes harder

With monitoring already configured:

Monitoring configured
        ↓
Metrics continuously collected
        ↓
Baseline established
        ↓
Thresholds/alerts configured
        ↓
Incident occurs
        ↓
Historical information available
        ↓
Faster investigation

Preconfigured monitoring provides valuable context.

For example:

CPU today = 90%

By itself, this may not tell the complete story.

Historical monitoring might show:

Normal CPU:
30–50%

Last 24 hours:
35–48%

Current CPU:
95%

This makes the abnormal behavior easier to identify.

14. What is a Metric?

A metric is a numerical measurement of the state or performance of a system over time.

Examples:

CPU Utilization = 75%
Memory Utilization = 68%
Network In = 20 MB
Network Out = 15 MB
Request Count = 10,000
Error Rate = 2%
Latency = 250 ms

Metrics are useful for:

Monitoring
Dashboards
Thresholds
Alerts
Capacity planning
Performance analysis

Example:

Time        CPU
10:00       35%
10:05       40%
10:10       55%
10:15       82%
10:20       91%

This makes it possible to identify trends.

15. What is a Log?

A log is a recorded event or message generated by a system, application, service, container, or operating system.

Example:

2026-09-13 10:15:01 INFO Request received
2026-09-13 10:15:02 INFO Processing request
2026-09-13 10:15:04 ERROR Database timeout

Logs can contain information such as:

Timestamp
Log level
Application name
Message
Error details
Request information
Process information
Exception details
16. Difference Between a Metric and a Log
Feature	Metric	Log
Type	Numerical measurement	Recorded event/message
Example	CPU = 90%	Database connection failed
Best for	Trends and thresholds	Detailed investigation
Alerting	Commonly used	Can also support alerts
Storage format	Time-series measurements	Event records
Detail	Usually summarized	Often more detailed
Example question	"How high is CPU?"	"Why did the application fail?"

Simple explanation:

Metric
  ↓
What is happening?

Log
  ↓
What happened and what details were recorded?

23. Monitoring Best Practices

DevOps engineers should follow several monitoring principles.

23.1 Monitor Important Resources

Monitor resources that directly affect application availability and performance.

23.2 Define Meaningful Thresholds

Avoid creating unnecessary alerts for normal fluctuations.

23.3 Avoid Alert Fatigue

Too many non-actionable alerts can cause engineers to ignore important alerts.

23.4 Keep Historical Data

Historical data helps identify trends and compare current behavior with normal behavior.

23.5 Monitor Before Production Incidents

Monitoring should already be working before a production incident occurs.

23.6 Protect Logs

Logs may contain sensitive information. Access should be controlled appropriately.

23.7 Document Alert Actions

The team should understand what to investigate when an alert fires.

25. Interview Questions and Answers
Q1. What is monitoring?

Monitoring is the continuous observation and measurement of system health and performance to detect abnormal conditions and failures.

Q2. What is logging?

Logging is the process of recording events, messages, errors, and activities generated by systems and applications.

Q3. What is an alert?

An alert is a notification generated when a configured monitoring condition or threshold is met.

Q4. What is observability?

Observability is the ability to understand a system's internal behavior and state from the telemetry it produces, commonly including metrics, logs, and traces.

Q5. Why do DevOps engineers monitor servers?

To detect problems early, maintain availability and performance, troubleshoot incidents, plan capacity, and improve reliability.

Q6. What can happen when CPU reaches 100%?

The system may experience increased latency, slow processing, request timeouts, application errors, or reduced availability depending on the workload.

Q7. Why configure monitoring before an incident?

Preconfigured monitoring provides historical data, baselines, dashboards, and alerts that help detect and investigate incidents faster.

Q8. What is the difference between a metric and a log?

A metric is a numerical measurement over time, while a log is a detailed recorded event or message.
