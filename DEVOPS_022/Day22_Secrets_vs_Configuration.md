TASK 4 — Secrets vs Normal Configuration

Training Area: DevOps / Docker
Time: 45 Minutes
Deliverable: Day22_Secrets_vs_Configuration.md

1. Objective

The objective of this task is to understand the difference between:

Normal configuration
Sensitive information / secrets

Applications require configuration to control their behavior, but sensitive values must receive stronger protection.

The basic concept is:

Application
     │
     ├── Normal Configuration
     │
     └── Sensitive Information
              │
              ↓
       Secret Management
2. Normal Configuration

Normal configuration contains values that control application behavior but are generally not secret by themselves.

Examples:

PORT
APP_ENV
LOG_LEVEL
API_URL
Example
PORT=5000
APP_ENV=development
LOG_LEVEL=DEBUG
API_URL=https://dev-api.example.com

These values may be stored outside the application source code and supplied through environment variables or configuration files.

However, "normal configuration" does not mean that every configuration value is automatically safe to publish. Each value should still be reviewed for sensitivity.

3. Sensitive Information

Sensitive information includes values that can provide access to systems, applications, databases, or protected resources.

Examples:

DATABASE_PASSWORD
API_SECRET
PRIVATE_KEY
ACCESS_TOKEN
REGISTRY_TOKEN

These values should be treated as secrets.

Example:

DATABASE_PASSWORD=<secret>
API_SECRET=<secret>
ACCESS_TOKEN=<secret>

Real secret values should never be placed in documentation or training files.

4. Normal Configuration List

The following are the normal configuration examples specified for this task:

PORT
APP_ENV
LOG_LEVEL
API_URL
PORT

Defines the network port used by the application.

Example:

PORT=5000
APP_ENV

Identifies the application environment.

Example:

APP_ENV=development

or:

APP_ENV=production
LOG_LEVEL

Controls the amount of logging generated by an application.

Example:

LOG_LEVEL=INFO
API_URL

Specifies the endpoint used by the application.

Example:

API_URL=https://api.example.com

A URL is generally not a secret, but it should still be reviewed for sensitive information before being committed.

5. Sensitive Information List

The following values should be treated as sensitive:

DATABASE_PASSWORD
API_SECRET
PRIVATE_KEY
ACCESS_TOKEN
REGISTRY_TOKEN
DATABASE_PASSWORD

Password used to authenticate to a database.

Example:

DATABASE_PASSWORD=<secret>
API_SECRET

Secret value used by an application or API for authentication or signing.

Example:

API_SECRET=<secret>
PRIVATE_KEY

A cryptographic private key.

Example:

PRIVATE_KEY=<private-key>

Private keys must be strongly protected.

ACCESS_TOKEN

A token that can provide access to an application or service.

Example:

ACCESS_TOKEN=<access-token>
REGISTRY_TOKEN

A credential/token used to authenticate with a container registry.

Example:

REGISTRY_TOKEN=<registry-token>
6. Which Values Can Safely Be Committed to Git?

The answer is:

Normal, non-sensitive configuration values can generally be committed to Git after reviewing them for sensitive information. Real secrets should not be committed to Git.

For this exercise:

Generally Safe After Review
PORT
APP_ENV
LOG_LEVEL
API_URL

Example:

PORT=5000
APP_ENV=development
LOG_LEVEL=INFO
API_URL=https://dev-api.example.com

These are generally acceptable in source control if they contain no credentials, tokens, private data, or other sensitive information.

Should NOT Be Committed
DATABASE_PASSWORD
API_SECRET
PRIVATE_KEY
ACCESS_TOKEN
REGISTRY_TOKEN

8. Why Should Secrets Not Be Committed?

Git repositories can be accessed by:

developers
CI/CD systems
external collaborators
organization members
public users if the repository is public

Once a secret is committed, it may remain in:

Git history
commits
branches
forks
pull requests
cached copies
CI/CD logs

Simply deleting the file in a later commit does not necessarily remove the secret from Git history.

Therefore:

Secret
  ↓
Do NOT commit
  ↓
Store securely
  ↓
Provide at runtime
9. Bad Example

Do not write:

DATABASE_PASSWORD = "MyProductionPassword"

Do not commit:

DATABASE_PASSWORD=RealProductionPassword

Do not commit:

ACCESS_TOKEN=real-production-token

Do not commit:

PRIVATE_KEY=real-private-key
10. Better Approach

Use a placeholder or environment variable:

import os

database_password = os.getenv("DATABASE_PASSWORD")

Then provide the secret through an approved runtime mechanism.

Architecture:

Secret Store / Secure Environment
              │
              ↓
       Runtime Environment
              │
              ↓
         Application

The application source code does not contain the actual secret.

11. .env Example

A local development .env file might contain:

PORT=5000
APP_ENV=development
LOG_LEVEL=DEBUG
API_URL=https://dev-api.example.com

DATABASE_PASSWORD=<development-secret>
API_SECRET=<development-secret>
ACCESS_TOKEN=<development-token>

If the file contains real secrets, it should normally be excluded from Git:

.env
12. .env.example

Instead of committing the real .env, commit a template:

PORT=5000
APP_ENV=development
LOG_LEVEL=DEBUG
API_URL=https://dev-api.example.com

DATABASE_PASSWORD=
API_SECRET=
ACCESS_TOKEN=

This tells developers which variables are required without exposing actual secret values.

A secure workflow can look like this:

    │
    ├── Application Code
    ├── Normal Configuration
    ├── .env.example
    └── .gitignore

The actual secret values are not committed.

14. Secret Management

For production systems, secrets should preferably be stored using an approved secret-management mechanism.

Examples include:

AWS Secrets Manager
HashiCorp Vault
CI/CD secret stores
Kubernetes Secrets
Docker secret mechanisms where appropriate

Architecture:

                 Secret Management
                        │
                        ↓
                  Secure Secret
                        │
                        ↓
                  Application
                        │
                        ↓
                    Runtime

The exact mechanism depends on the deployment platform and organizational security requirements.

15. Docker Example

Docker applications commonly receive configuration at runtime.

Example:

services:
  app:
    image: myapp:1.0
    environment:
      PORT: ${PORT}
      APP_ENV: ${APP_ENV}
      LOG_LEVEL: ${LOG_LEVEL}
      API_URL: ${API_URL}
      DATABASE_PASSWORD: ${DATABASE_PASSWORD}

The application can read the values without putting the actual values into the Docker image source code.

Important

Passing a secret as an environment variable can be useful, but it does not make the secret automatically secure. Depending on the platform and threat model, secrets may be exposed through process inspection, debugging, logs, configuration output, or other mechanisms.

Use the platform's appropriate secret-management features when available.

18. What If a Secret Is Accidentally Committed?

If a real secret is accidentally pushed to Git:

1. Stop treating it as secret
        ↓
2. Revoke / deactivate it
        ↓
3. Rotate or replace the credential
        ↓
4. Investigate possible exposure
        ↓
5. Remove the secret from repository history as appropriate
        ↓
6. Update applications with the new credential
        ↓
7. Review security logs where appropriate

The most important immediate action is generally to revoke or rotate the exposed credential.

Simply deleting the file is not sufficient.

20. Security Rules

Remember these rules:

Rule 1

Never commit real passwords.

Rule 2

Never commit API keys or access tokens.

Rule 3

Never commit private keys.

Rule 4

Never commit registry credentials.

Rule 5

Use .env.example for documenting required variables.

Rule 6

Use .gitignore to prevent accidental commits of local secret files.

Rule 7

Use proper secret-management systems for production.

Rule 8

If a real secret is exposed, revoke/rotate it immediately.

Rule 9

Do not print secrets in application logs.

Rule 10

Review configuration before pushing code to Git.

21. Interview Questions
Q1. What is the difference between configuration and a secret?

Configuration controls application behavior, while a secret is sensitive information that can provide access to protected systems or resources.

Q2. Can PORT=5000 be committed to Git?

Generally yes, assuming it does not contain sensitive information.

Q3. Can a database password be committed to Git?

No. Real database passwords should not be committed to source control.

Q4. Can an API URL be committed to Git?

Usually yes if it is a non-sensitive endpoint. However, it should be reviewed to ensure it does not contain embedded credentials, tokens, private information, or other sensitive data.

Q5. What should you do if an access token is accidentally pushed to GitHub?

Treat it as compromised, revoke or rotate it immediately, investigate exposure, and remove it from repository history as appropriate.

Q6. Is an environment variable automatically secure?

No. Environment variables are a configuration mechanism, not a complete security mechanism.
